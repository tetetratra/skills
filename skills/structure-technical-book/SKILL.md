# 技術書全体を構造化する

## 目的

技術書全体を、原文の構造と順序を保った複数のMarkdownファイルへ変換する。
各文章を独立した文脈で処理し、先に変換した文章の内容が後続文章の解釈へ影響することを防ぐ。

## 入力

次の値を受け取る。

- `source`：書籍本文を含むファイル、ディレクトリ、またはユーザーから渡された本文
- `file_granularity`：1ファイルにまとめる原文上の単位
  - 例：章ごと、節ごと、項ごと、見出しレベル2ごと
- `output_directory`：出力先ディレクトリ
  - 省略された場合は、入力元と同じ場所に `{書籍名}-structured` を作る

`source` または `file_granularity` が不足している場合だけ、作業開始前にユーザーへ確認する。

呼び出し例：

```text
$structure-technical-book
source: ./books/example.epub
file_granularity: 節ごと
output_directory: ./output/example
```

## 単位の区別

ファイル単位と変換単位を分けて扱う。

- **ファイル単位**：`file_granularity` で指定された、1つのMarkdownファイルにまとめる範囲
- **変換単位**：ファイル単位の内部にある、原文上の最小の見出し単位

章ごとに出力する場合でも、章内に節や項があれば、節や項を別々の変換単位として扱う。
変換単位ごとに新しい独立エージェントを起動し、複数の変換単位を同じエージェントへ渡さない。

ファイル単位の内部に下位見出しがない場合は、ファイル単位そのものを一つの変換単位とする。
親見出しの直下に導入文があり、導入文の後から下位見出しが始まる場合は、導入文を親見出しの変換単位として扱う。
本文を持たない見出しには、空の変換単位を作らない。
段落しか存在せず、指定粒度を原文から判定できない場合は、見出しや番号を推測で作らずユーザーへ確認する。

## 手順

### 1. 変換規則を読み込む

`structure-technical-text` の `SKILL.md` を全文読み、文章の位置づけ、内容固有のブロック、名詞句、関係の明示、ネスト、情報価値、文献引用マーカー、太字に関する規則を使用する。

### 2. 書籍構造を抽出する

- 目次、PDFブックマーク、EPUBのナビゲーション、HTML見出し、Markdown見出しなど、入力形式が持つ構造情報を優先する。
- 章番号、節番号、項番号、見出し名、出現順序を原文どおりに保持する。
- 序文、付録、用語集などの番号がない要素も、原文の見出しを保持して対象に含める。
- 参考文献、引用文献、Bibliography、Referencesなど、内容の大半が書誌情報である章や節は変換対象から除外する。
  - 参考文献一覧だけで構成されるファイル単位には、出力ファイルを割り当てない。
  - 本文と参考文献一覧が同じファイル単位に含まれる場合は、参考文献一覧だけを除外する。
- 各本文が一つの変換単位だけに属するよう境界を定め、重複と欠落を防ぐ。
- 本文から離れた脚注や注記は、参照元を特定できる場合は参照元の変換単位に含める。

書籍構造を、次の情報を持つ作業用一覧としてメモリ上に整理する。

- 原文上の順序
- ファイル単位の番号と見出し
- 変換単位の番号と見出し
- 親見出しから変換単位までの構造パス
- 変換単位のMarkdown見出しレベル
- 変換対象となる本文の範囲
- 参考文献一覧として除外する範囲
- 出力ファイル名

作業用一覧を中間ドキュメントとして出力しない。

### 3. 出力ファイルを割り当てる

- `file_granularity` と一致する原文単位ごとに、一つのMarkdownファイルを割り当てる。
- ファイル名には、並び順と原文の番号・見出しが判別できる名前を使う。
- 原文に番号がある場合は番号を保持する。
- 原文に番号がない場合は、原文順を表すゼロ埋め連番を先頭に付ける。
- `/`、`\`、`:`、`*`、`?`、`"`、`<`、`>`、`|` など、ファイル名に使えない文字だけをハイフンへ置き換える。
- 同名ファイルが発生する場合は、原文順の連番を付けて衝突を避ける。
- 指定粒度より上位の見出しに直属する本文は、上位見出しの番号と名前を持つ独立ファイルへ出力する。
- 参考文献一覧として除外したファイル単位には、空のMarkdownファイルを作らない。

### 4. 変換単位ごとに独立エージェントを起動する

利用可能なサブエージェント起動機能を使い、変換単位ごとに新しいエージェントを起動する。

- 親会話を継承しない新規コンテキストを使う。
  - `fork_context` を指定できる場合は `false` にする。
- `structure-technical-text` をスキルとして添付または明示的に読み込ませる。
- エージェントへ渡す書籍内容は、対象となる変換単位の構造パス、見出し、Markdown見出しレベル、本文だけに限定する。
- 前後の変換単位、書籍全体の要約、別エージェントの出力を渡さない。
- 一度使ったエージェントを別の変換単位へ再利用しない。
- 並列実行する場合も、一つのエージェントには一つの変換単位だけを割り当てる。
- エージェントを使い終えたら閉じる。

変換が失敗した場合は、失敗したエージェントを再利用しない。
同じ構造パス、見出し、Markdown見出しレベル、本文だけを渡した新しいエージェントを起動し、形式上の問題点だけを追加で伝える。

### 5. 独立エージェントへ変換を依頼する

書籍の章を見出しレベル1とし、下位階層へ進むごとにMarkdown見出しレベルを一つ深くする。
たとえば、`10 章名` は `#`、`10.1 節名` は `##`、`10.1.1 項名` は `###` を使う。
番号のない見出しも、原文上の階層に基づいて見出しレベルを決める。

各エージェントへ、次の指示を渡す。

```text
$structure-technical-text を使い、入力本文だけを構造化してください。

書籍内の見出し：{原文どおりの番号と見出し}
書籍内の構造パス：{親見出しから対象見出しまでの番号と名前。本文は含めない}
Markdown見出しレベル：{原文上の階層に対応する1から6の整数}
本文：
{対象となる変換単位の本文だけを記載}

出力規則：
- 書籍内の見出しを、指定されたレベルのMarkdown見出しとして原文どおりに記載する
- Markdown見出し直後に「この文章について」を置き、構造パスを踏まえた文章の位置づけを書く
- 「この文章について」には具体的な要約や結論を書かない
- 「主張概要」と「本文構造」を出力しない
- 本文は、対象や関係が分かる内容固有のラベルを最上位として構造化する
- 名詞句で意味が完結する要素は名詞句にする
- 名詞句で対象や関係が曖昧になる場合は、関係を含む短い文章にする
- 補足、理由、具体例、条件、結果は説明対象の子要素にする
- 親子関係を表せる内容は、並列にせずネストする
- ネストが深くなる場合でも、親子関係を平坦化しない
- 書籍の趣旨から外れる余談、自明な説明、具体的な価値を持たない要素を削る
- `[5]`、`［5］`、`[3, 4]`など、参考文献一覧への参照だけを示す文献引用マーカーを削る
- 文献引用マーカーが付いていた主張や事実は残す
- 脚注番号、章節番号、コード中の添字は削らない
- 重要な主張や判断基準だけを太字にし、太字を含む箇条書き要素を全要素の10分の1未満にする
- 書籍内の見出しを除き、入力本文にない情報を加えない
- 他の章や節の内容を推測しない
- 変換結果だけを出力する
```

エージェントの出力は、次の形にする。

```markdown
### 10.x.y ZZZについて

- この文章について
  - {書籍内または議論の流れにおける位置づけ}
- {対象や関係が分かる内容固有のラベル}
  - {名詞句で完結する情報}
  - {説明対象}
    - {補足、理由、具体例、条件、または結果}
- {別の内容固有のラベル}
  - {関係を省略できない場合の短い文章}
```

Markdown見出しの番号と名前は原文をそのまま使用する。
Markdown見出しに指示語が含まれる場合も、見出しは変更しない。

### 6. ファイルへ集約する

- 各エージェントの出力を、対応するファイル単位のMarkdownファイルへ原文順で並べる。
- 一つのファイルに複数の変換単位が含まれる場合は、原文の階層に対応するMarkdown見出しを複数並べる。
- 変換結果の間には空行を一つ置く。
- 集約時は文章を要約、統合、言い換えしない。
- 書籍全体を再解釈する統合エージェントを起動しない。
- 親エージェントは形式と配置だけを扱い、変換内容を編集しない。

出力例：

```markdown
## 10.2 Proc

- この文章について
  - Procの基本概念から具体的な生成方法へ進む節の導入
- Proc
  - 定義
    - ...

### 10.2.1 Procの生成

- この文章について
  - Procの生成方法を分類する項
- 生成方法
  - 非lambdaのProcを生成
    - ...

### 10.2.2 lambdaとの違い

- この文章について
  - lambdaと非lambdaのProcを選ぶための比較
- 引数の扱い
  - lambda
    - ...
```

### 7. 完全性と形式を検証する

- 参考文献一覧として除外した単位を除き、出力対象のファイル単位ごとにMarkdownファイルが一つだけ存在するか確認する。
- 参考文献一覧として除外した単位を除き、すべての変換単位が一度ずつ出力され、重複や欠落がないか確認する。
- 参考文献一覧として除外した章や節、および空の出力ファイルが生成されていないか確認する。
- ファイルとMarkdown見出しが原文順に並んでいるか確認する。
- Markdown見出しの番号と名前が原文と一致するか確認する。
- Markdown見出しレベルが原文の章・節・項の階層と一致するか確認する。
- 各Markdown見出し直後に「この文章について」が一つだけ存在するか確認する。
- 「この文章について」が要約ではなく、構造パスや議論における位置づけを示しているか確認する。
- 「主張概要」と「本文構造」が残っていないか確認する。
- 内容ブロックのラベルだけを読んでも、対象と情報の関係が分かるか確認する。
- 名詞句への変換によって、主語、対象、作用、比較、因果が欠落していないか確認する。
- 親子関係を持つ内容が不必要に平坦化されていないか確認する。
- 情報価値の低い要素が残っていないか確認する。
- 参考文献一覧を指す文献引用マーカーが残っていないか確認する。
- 脚注番号、章節番号、コード中の添字を誤って削除していないか確認する。
- 各ファイルと全出力を通して、太字を含む箇条書き要素が全要素の10分の1未満か確認する。
- 各エージェントが一つの変換単位だけを処理したか確認する。
- 空ファイルや変換失敗の文言が残っていないか確認する。

形式上の問題がある変換単位だけを、新しい独立エージェントで再変換する。

## 制約

- 変換単位の本文がエージェントのコンテキスト上限を超える場合、本文を途中で切り捨てない。
- より細かい原文上の見出しで分割できる場合は、見出し単位を変換単位として使う。
- 原文上の境界で分割できない場合は、該当箇所と理由をユーザーへ伝え、入力の分割方法を確認する。
- 出力先に今回の処理と無関係なファイルがある場合は、削除や上書きを行わない。
- 原文の見出し、引用、コードに含まれる表現は保持する。変換本文では `structure-technical-text` の指示語に関する規則を適用する。
