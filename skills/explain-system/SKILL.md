## 目的

- 既存のシステムや機能の仕組みを調査し、ユーザーが理解しやすい文書にまとめる
- タスクの文脈がある場合は、後続の要求定義、要件定義、対応方針決めに必要な判断材料を揃える

このスキルでは調査結果の整理までを行います。
対応方針の決定や詳細設計は行わないでください。

## 範囲の決め方

入力によって、調べる範囲を切り替えてください。

- タスクの文脈がある場合（例：「この機能に〇〇を追加したい。関係する仕組みを調べて」）
  - タスクに関係する部分に絞って調べる
  - 必要なら、関連技術や類似実装・前例の視点も加える
- 機能やシステムの名前だけが指定された場合（例：「Q&A機能について説明して」）
  - その機能の全体像を網羅的にまとめる
  - 関係する場合は、ビジネスコンテキストと詳細設計まで含める

どちらか判断がつかない場合は、ユーザーに確認してください。

## 手順

1. `## 視点の一覧` から、今回まとめる際の視点を選んでください
   - `既存システムの概要` は原則として含めてください
   - 小見出しはユーザーの負担を考慮して最低限にしてください。タスクの文脈がある場合は、数個以内に収めてください
2. 各視点ごとに、必要なコード、既存ドキュメント、チケット、参考資料を調査してください
3. 各視点ごとに、調査結果を小見出し内へ整理してください（`## 書き方` に従う）
4. 調査の途中で新しい論点が見つかった場合は、必要に応じて視点を追加・修正してください

## 視点の一覧

- **既存システムの概要**
  - そのシステムや機能が何をするもので、どんな構成になっているかを述べる
- **ビジネスコンテキスト**
  - 解決する課題、ターゲットユーザー、提供価値など、システムの存在意義（Why）を述べる
- **主要なモデル・コンポーネント**
  - 理解する上で最低限押さえておくべきモデル・コンポーネントを列挙し、それぞれの役割・責務と境界を説明する
- **動作フロー**
  - 対象とするユースケース（シナリオ）ごとに、ユーザー操作に伴う処理や状態の変化を順に説明する
  - シーケンス図やフローチャートを添える
- **データ構造・テーブル構成**
  - テーブルの概要と、ドメイン上重要なカラムの意味を説明する
  - ER図を添える
- **詳細設計**
  - クラス設計：ディレクトリ・ファイルごとに1段ずつインデントを下げ、ファイルの内容と役割、重要なpublicメソッドの簡潔な説明を書く
    - `belongs_to:` や `scope:` や `is_xxx?` などの、動詞ではない関数は基本的に書かない
  - API設計：エンドポイントごとに用途と処理内容、リクエスト・レスポンスの例を書く
  - 関係しないもの（テーブルやAPIのない機能など）は省略する
- **関連技術**
  - アプリケーションの仕様説明ではなく、今回の理解に必要な一般的な技術や概念を扱う
  - その技術が広く知られた一般的なものなら無理に書く必要はない
  - 深く掘り下げる必要がある場合は、`concept-tree` スキルの利用を提案する
- **類似実装・前例**
  - 今回の理解に役立つものがある場合だけ選ぶ

## 書き方

- 事実・推測・未確認事項が混ざらないようにしてください
  - 推測が入る場合は、その根拠と推測であることを明記してください
  - 調べても分からない箇所は、憶測で書かず、不明であることを明記してください
- `事実:` や `根拠:` のような不自然な接頭辞は付けず、自然な文章で整理してください
- 調査メモの断片を並べるのではなく、短い前提整理ドキュメントのつもりで、少し丁寧に・少し構造化して書いてください
- 1つの箇条書きでは、最初に全体像や結論を1文で述べ、その後に必要な補足を続けてください
- 識別子の扱い
  - `詳細設計` 以外の視点では、まずユーザーが追える単位で説明してください。関数名や変数名は、ユーザーが把握していないことが多いため、基本的には書かないでください
  - 画面名、機能名、コンポーネント名、モデル名など、ユーザーが把握している可能性が高い名前は、必要な範囲で書いて構いません
  - `詳細設計` の視点では、ファイル名、クラス名、メソッド名、テーブル名、カラム名を書いて構いません
- 図示したほうが分かりやすい箇所は、mermaid で図示してください。アスキーアートは使わないでください

## 出力フォーマット

```
## {システム名 / 機能名}の調査結果

### {小見出し}
- {調査結果}
  - {必要に応じて補足}
  - ...
- ...
```

## 出力例

コードブロック内にコードブロックを置くと表示が崩れるので、例ではバッククォート2個で表現しています。

### タスクの文脈がある場合

「質問投稿機能に、投稿者への承認通知を追加したい」というタスクで、関係する仕組みを調べた例です。

```
## 質問投稿機能の調査結果

### 既存システムの概要
- 質問投稿機能は、投稿画面で受け付けた内容を `questions` テーブルへ保存し、モデレーター画面の確認後に一覧へ反映する構成
  - 投稿内容は `Question` モデルとして扱われ、投稿直後に全体公開するのではなく、`status` カラムが `published` になっているレコードだけを表示対象にする前提
- ...

### 動作フロー
- 視聴者が投稿画面から質問を送信すると、バックエンドで `Question` レコードが作成され、モデレーター画面から確認できる状態になる
  - 保存時点では公開状態（`status: published`）にならず、確認待ち（`status: pending`）の扱い
- モデレーターが承認すると、公開対象の一覧に含まれる
  - 承認操作を起点に、質問一覧コンポーネントから見える公開対象へ反映
- ...
``
flowchart LR
  A[質問投稿画面] --> B[保存<br/>Question レコード作成]
  B --> C[モデレーター画面で確認]
  C --> D[承認]
  D --> E[公開一覧に反映<br/>status: published]
``
```

### 機能名だけが指定された場合

「リアルタイムQ&A・モデレーション機能について説明して」と依頼された例です。

```
## リアルタイムQ&A・モデレーション機能の調査結果

### ビジネスコンテキスト
- 数千人規模のイベントで、不適切な質問を排除しつつ円滑に質疑応答を行うための機能
  - ターゲットユーザーは、講演会の視聴者、運営モデレーター、登壇者
  - 双方向性の高い講演会を、低リスクかつ効率的に運営できることが提供価値

### 主要なモデル・コンポーネント
- 投稿UIは、視聴者からの入力を受け付け、バリデーションを行う
  - 匿名投稿の有無や文字数制限などのルールを適用する
- ...

### 動作フロー
- 視聴者が投稿した質問が承認され、全体に公開されるまでの流れ
  1. 視聴者が投稿すると、バリデーションを経て「未承認」状態でDBへ保存される
  2. モデレーター管理画面へ、新着質問の通知がリアルタイムに送信される
  3. モデレーターが承認すると、DBのステータスが更新され、全視聴者へ配信イベントが発行される
  4. 各クライアントのUI上で、対象の質問がリストに追加表示される
``
sequenceDiagram
  ...
``

### 詳細設計
- app/
  - controllers/
    - questions_controller.rb: 視聴者からの投稿およびモデレーターの承認アクションを制御する
      - #approve: 質問のステータスを公開に変更し、配信イベントを発火させる
- POST /api/v1/questions: 視聴者が新しい質問を投稿する
  - リクエスト: { "content": "質問内容...", "is_anonymous": true }
  - レスポンス: { "id": "q_123", "status": "pending" }
```

## 注意点

- 対応方針決めなどはこのスキルでは行いません。出力しないでください
- 調査結果と意思決定を混ぜないでください
- 事実に基づく説明を優先し、判断が必要な点は未解決事項として補足的に明記してください
