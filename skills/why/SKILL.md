## 目的

ある問題に対してとった解決策について、「なぜそれが要るのか」「なぜそれで問題を防げるのか」を説明文で伝えます。

- 書く場所は問いません（コードコメント、PR 本文、コミットメッセージ、設計メモ、障害報告、チャットでの説明など）。
- 読み手は、そのドメイン（仕様、業務の決まり、使っているライブラリやサービスの内部）に詳しくない人を想定します。

## ルール

### 1. 概要 → 前提 → 問題 → 解決 の順に書く

- **概要**: 最初の 1 文で、その解決策が何のためのものかを書きます。
- **前提**: 話の対象ごとに分けて 1 つずつ出します。仕様や業務の決まりなどの外側の決まりを先に、それを使う仕組み（ライブラリ、コード、運用）の動きをあとに書きます。
- **問題**: 前提を出し終えてから書きます。前提の説明の途中に問題を混ぜません。
- **解決**: 最後に、どう解決したかを書きます（「そこで〜」）。

### 2. 用語の初出には、括弧で「何か」を添える

- ドメインに詳しくない読み手が「〜って何？」と止まる語には、初出で括弧の補足を付けます。
- 他動詞の目的語を省きません（「暗号化するだけで」ではなく「パスワードを暗号化するだけで」）。
- 補足は、説明の対象から見て正確な言い方にします。受け取る側の仕組みの説明なら、送る側の経路ではなく、受け取る側に見える形で書きます。

### 3. つながりに要る事実は省かない

- 解決策がなぜ問題を防げるのかを、前提の中で説明しておきます。前提が欠けていると、読み手は解決と問題の関係をたどれません。
- 問題が起きる条件（いつ、どんなときに起きるか）を書きます。「〜することがある」で済ませません。

### 4. 長さ

- 並べ替えや補足で、文の量を大きく増やしません。補足で 1 文が長くなったら、文を分けます。

## 例（架空の事例）

決済サービスの Webhook で同じ通知が送り直され、ポイントが 2 回付くのを防ぐ解決策を説明する例です。

### 悪い例（コードコメント）

```
# 通知 ID を記録し、記録済みの ID なら true を返す。
# 決済サービスの Webhook は同じ通知が届くことがあり、
# handle_payment_completed は受け取るたびにポイントを付けるので、同じ決済に 2 回ポイントが付いてしまう。
# Webhook は決済の結果を POST で知らせる仕組みで、決済サービスの決まりに従って送られてくる。
# 通知 ID で重複を判定しているので、二重にポイントが付かない。
# 決済完了の通知を処理するときに使う。
```

- 解決から書き始めていて、概要（ポイントを 2 回付けない）が文の途中に埋もれている
- 前提と問題が 1 文に混ざり、そのあとで前提（Webhook とは何か）に戻っている
- 同じ通知が届く条件（受け取ったことを返せなかったとき）が抜けていて、「ことがある」ではいつ起きるのか分からない
- 「通知 ID」が何かの補足がなく、なぜそれで重複を判定できるのかをたどれない
- 最後の行は用途の付け足しで、話の流れから外れている

### 良い例（コードコメント）

```
# 決済完了の通知を二重に処理して、ポイントを 2 回付けないようにする。
# Webhook（決済サービスが、決済の結果をこちらの URL に POST で知らせる仕組み）は、
# 受け取ったことを決済サービスに返せなかったときに、同じ通知を送り直す決まりになっている。
# このメソッドを呼ぶ handle_payment_completed は、通知を受け取るたびにポイントを付ける。
# このため、応答がタイムアウトして通知が送り直されると、同じ決済に 2 回ポイントが付く。
# そこで通知 ID（決済サービスが通知ごとに振る ID）を記録し、記録済みの ID なら true を返す。
```

- 概要→前提→問題→解決 の順で文章が組み立てられている
- 外側の決まり → 仕組みの動き → 問題、と 1 つずつ出すので、話の対象が途中で入れ替わらない
- 「Webhook」「通知 ID」に括弧で補足があり、ドメインを知らなくても読める
- 送り直しが起きる条件が前提にあるので、ID の記録で問題を防げる理由がつながる
